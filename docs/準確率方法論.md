# 準確率方法論 —— 怎麼判斷題目好不好、怎麼把面板調準

這份文件講的是「怎麼改進問題，讓 42 維度的數值更貼近真實」。
搭配後台的「選項數據」頁（`server/admin/stats.html`）一起看：頁面上半部的「題庫體檢」
就是這裡說的靜態指標，現在就能跑。

配套閱讀：`overview guide.txt`（設計原則）、`server/README.md`（後台）。

---

## 一、這套工具的「準確」是什麼

除了區塊一的客觀填空（伏地挺身數、跑步配速…），**其餘 38 個維度沒有外部標準答案**。
所以「準確」不能用「答對率」量，只能拆成四個可觀察的性質：

| 性質 | 白話 | 怎麼量 |
|---|---|---|
| **信度** | 同一個人、同一份答案 → 同一張面板；區塊四重測區塊二/三的維度，兩者該一致 | 計分是純函數（已達成）；跨區塊落差 `spread`（見 `score()`）；重測對比 |
| **鑑別力** | 每題真的能把不同的人分開 | 選項分數分佈範圍；（有資料後）選項實際被選比例；題—總分相關 |
| **構念效度** | 客觀錨點（區塊一）與同維度的自評題方向一致 | 每人「區塊一推得的硬件值」對「區塊二/三自評值」 |
| **覆蓋與非冗餘** | 每個維度 ≥3 題、跨區塊，沒有單題決定的維度 | 題庫體檢的「維度覆蓋」表 |

## 二、槓桿，依優先序

**先改結構性的（1–4），再談引擎（6）。** 每一項對應題庫體檢頁上的一張表。

### 1. 補「覆蓋薄弱」的維度

`score()`（`index.html`，`function score()`）對每個維度收集三桶分數：
`obj`（區塊一）、`self`（區塊二/三）、`cross`（區塊四），最終
`raw = 0.45·mean(self) + 0.55·mean(obj+cross)`。

- 只有 `self`、沒有 `obj` 也沒有 `cross` → 退化成 `raw = self − 0.6·bias`（夾在 ±0.8）。
  **這種維度最不可信**，因為它完全靠受測者的自我評估，沒有任何錨點。
- 沒有 `cross` → 區塊四沒有重問它，偵測不到這個維度的自評偏差。

> **目前狀況**：`bal`（平衡）、`eye`（手眼協調）、`fin`（精細動作）、`flx`（柔韌性）、`pow`（爆發力）
> 這五個硬件維度**沒有任何區塊四交叉校驗題**，各只有 1 客觀 + 2 自評。
> 改法：在區塊四加一題用「他人觀察 / 可回想的事實」重問（例：柔韌性 →
> 「彎腰撿東西、綁鞋帶時，你會不會覺得卡」）。

### 2. 修區塊三「退化成排序題」的題

區塊三的設計前提是**選項是風格差異、沒有明顯最優解**（`overview guide.txt` 第四節）。
如果一個選項在它涉及的每個維度上都 ≥ 其他每一個選項（Pareto 支配），這題就有標準答案了：
知道自己的人選對的，想刷高分的人也選同一個 —— 兩種人分不開。

> **目前狀況**：58 題區塊三裡，**28 題**有支配選項，而且這 28 題全部是「所有選項觸及同一組維度、
> 數值變成一條排序」的形態（體檢頁標成 `退化成排序題`）。
> 例：abs 56「戶外活動下大雨」的選項 C 是 `{adp:5, tim:5, ldr:5}`，直接三個維度都頂格。
>
> 兩條改法（每題挑一條）：
> - **改成真正的取捨**：讓不同選項在不同維度上各有得失。
>   例：「馬上宣布改室內」→ 應變力高、但組織力普通；「撐到最後一刻再決定」→ 統籌高、但應變普通。
> - **搬去區塊一/二/四**：如果這題問的其實是「你多會處理臨時狀況」這種可排序的事，
>   那它就該用有序選項（A 最弱 → E 最強）放到別的區塊，不要假裝是取捨題。

### 3. 修區塊一/二/四選項不單調的題

這三個區塊的選項出題時就按「A 最弱 → E 最強」排好，所以選項總分該遞增。
不遞增 = 認題錯誤（某個選項的 `s:{}` 分數填錯位置）。

> **目前狀況**：0 題。這是回歸檢查，之後改題時再看。

### 4. 修不鑑別的題

選項總分幾乎沒有差距、或某個維度在每個選項都給同一個分數 → 這題分不出人，
白佔一個題位還稀釋維度分（維度分是「該維度累計分 ÷ 涉及題數」）。

> **目前狀況**：0 題（體型傾向的五題判定題只餵 soma 軸、不算能力分，已排除）。

### 5. 硬件／軟件平衡

軟件維度 24 個、硬件能力維度只有 14 個。場景若照「想得到就寫」累積會偏向軟件，
結果頁的「最吃得開／最吃力八件事」就看不到身體項目。

> **目前狀況**（對得上 `overview guide.txt`）：硬件主導場景 34/93，含任何硬件維度的場景 53/93（57%）。
> 每個硬件維度的場景涵蓋數最低 4（爆發力、聲音條件）、平均約 9。
> 若之後加場景，盯著「硬件主導比例」和「每個硬件維度被幾個場景涵蓋」兩個數字，別讓它們掉。

### 6. 最後才調計分引擎

`index.html` 的 `score()` 裡有幾個手調參數：

| 位置 | 現值 | 意思 |
|---|---|---|
| `raw = 0.45*s + 0.55*anchor` | 45/55 | 自評 vs 客觀錨點的混合權重 |
| `raw = s - clamp(0.6*bias, ±0.8)` | 0.6 係數、±0.8 夾限 | 只有自評時的偏差校正力度 |
| `extremity - 0.35` | 0.35 | 「幾乎每題選最強選項」的容忍門檻 |
| `reliability = 100 - spread*20 - exPen` | ×20 | 可信度公式 |

**不要憑感覺調這些。** 要調的前提是「有真實作答資料，看得到 `bias` / `spread` / `extremity`
在真人身上的實際分佈」——那是第三階段的事。現在動它們只是換一組沒有根據的數字。

## 三、現在能算 vs. 需要作答資料

| 指標 | 需要作答資料？ | 在哪 |
|---|---|---|
| 維度覆蓋 / 區塊分佈 | 否 | 體檢頁「維度覆蓋」 |
| 區塊三支配選項 / 退化成排序題 | 否 | 體檢頁「無最優解稽核」 |
| 區塊一/二/四單調性 | 否 | 體檢頁「選項單調性」 |
| 選項分數分佈範圍 | 否 | 體檢頁「鑑別力（靜態）」 |
| 硬/軟件題量與場景平衡 | 否 | 體檢頁「硬件／軟件平衡」 |
| 選項實際被選比例（死選項：>65% 或 <5%） | **是** | 待做 |
| 題—總分相關（校正後，判斷這題到底在測什麼） | **是** | 待做 |
| 各維度的自評—錨點系統性落差 | **是** | 待做 |
| `extremity` / `reliability` 的真人分佈 | **是** | 待做 |
| 重測穩定度（同一個人隔幾天再測） | **是** | 待做 |

## 四、路線圖

- **階段一（已完成）**：靜態題庫體檢 + 本文件。
- **階段二**：`finish()`（`index.html`，算完 `RESULT_CODE` 之後）`POST /api/responses`，
  送**完整壓縮碼 + 摘要**（hw/sw 平均、reliability、bias、spread、extremity）。
  把 `decodeAns`（`index.html`）與精簡版 `score()` 移植到 Node，收到時還原逐題答案寫入 `submission_answers`。
- **階段三**：在「選項數據」頁的下半部加入上表「需要作答資料」那幾項。
- **階段四**：依前三階段累積的證據，調整 `score()` 的手調參數。

## 五、常駐限制：改題與存檔版本

- **純內容編輯**（改題幹文字、改選項文字、改選項的維度加分）→ 安全，重跑 `npm run import` 即可。
- **新增／刪除／換順序整題** → 會位移絕對題號，`index.html` 裡的 `const KEY` 與 `const CODE_VER`
  必須**一起遞增**（見 `overview guide.txt` 最後一節），否則舊存檔與舊壓縮碼會對到錯的題目上。
  後台編輯器因此只開放內容編輯，`POST` / `DELETE` 整題維持 501。
- 目前後台的編輯**只寫進資料庫，不會回寫 `index.html`**，所以還不影響線上測驗。
  回寫（或讓前端改讀 API）是階段二的一部分。
